# Reproducible performance captures

The unit of performance is one **complete display frame**, including every local
camera and one presentation. The initial 30 FPS target is 33.333 ms per complete
frame. Per-view render times must not be converted independently into game FPS.

See [the implementation report](README.md) for measured results and their limits,
[renderer details](renderer.md) for counter coverage, and [the Pi procedure](pi-zero2.md)
for hardware validation. Captures and diagnostic fixtures do not change default
gameplay populations, wave rules, collision or weapon behavior.

## Build and content controls

Use an isolated checkout and an optimized build:

```sh
make -j2 VERBOSE=1 with_gles1 > build-release.log 2>&1
```

The Makefile uses its release flags unless DEBUG/sanitizer options are selected.
Check the actual compiler command lines, not just the output directory name.
If using CMake, explicitly select Release; the existing default is Debug.

Each runtime needs the executable, matching renderer libraries, `baseq2/game.so`,
the user's complete game data and the generated `baseq2/plastic-platoon.pk3`.
Do not copy the benchmark configuration into a normal playing installation.
The runner writes only inside the supplied isolated runtime.

**Asset precedence matters:** numbered stock PAKs override loose model files in
this engine. The deterministic project PK3 generated by `make all`, `make pi`,
or `make assets` gives the actual project models precedence. Check the startup
log for that archive and record its hash. Early host trials without the archive
rendered stock geometry and were excluded from the reported Plastic Platoon
comparisons. Compressed PNG size is not texture memory usage.

For equivalent-content engine comparisons, use original assets in both runtimes.
For asset comparisons, use the same optimized engine and settings in both:

```sh
git worktree add --detach ../plasticPlatoon-baseline f2d9366ec7d2bbd256b5d103f1a57c6a5e1b011b
git -C ../plasticPlatoon-baseline apply "$PWD/tools/performance/baseline-instrumentation.patch"
make -C ../plasticPlatoon-baseline -j2 VERBOSE=1 with_gles1

python3 tools/assets/build_overlay.py \
  --source ../plasticPlatoon-baseline/baseq2 \
  --output /path/to/baseline/baseq2/plastic-platoon.pk3
python3 tools/assets/build_overlay.py \
  --source ../plasticPlatoon-baseline/baseq2 \
  --output /path/to/engine-only/baseq2/plastic-platoon.pk3
python3 tools/assets/build_overlay.py \
  --source baseq2 --output /path/to/optimized/baseq2/plastic-platoon.pk3
```

The baseline patch adds complete-frame/camera timing, the same benchmark commands
and build hooks to the pinned original source. It does not contain effect or
renderer optimizations. Original renderer-specific counters and effect counters
are unavailable and explicitly recorded as -1. The patched baseline preserves
the original simulation, rendering and asset algorithms.

Keep all three stock PAKs, map BSPs, game modules, resolution, camera settings,
VSync, frame limit, quality settings and process environment comparable. Do not
call a shader backend comparison against a fixed-function backend an engine
optimization result. Keep the low-end quality preset in a separate category.

## Five required scenarios

| Scenario | State and controls | Evidence to retain |
| --- | --- | --- |
| Single-player quiet sandbox | Fixed map/save, stationary camera, no combat during capture | Actual camera, active entities, complete-frame distribution |
| Two players in approximately the same area | Two actual local clients, nearby non-overlapping cameras; same total framebuffer | Both view sizes/cameras, aggregate and per-view submission, shared effect counts |
| Two players in different areas | Same map/save and settings; cameras in different leaf/area regions | PVS cache hits/builds, area correctness, both entity sets |
| Combat | Fixed recorded demo for single-player comparisons; repeatable native event fixture or carefully controlled real two-player state for split screen | Projectiles, temp events, particles, lights, lightmap uploads, CPU and optional GPU samples |
| Sustained waves | Actual map with its normal timer/spawner rules; capture beyond the final delayed wave delivery | Living/dead monster flags, all in-use edicts, particles, RSS, slow frames and displayed cadence |

For the supplied sandbox, ordinary placed lights are compile-time baked-lighting
inputs. They are not 118 runtime dynamic lights. Do not infer submitted triangles
from the 92-instance asset inventory; use the renderer counters for actual views.

The supplied source's wave progression is driven by triggers, timers and relays,
not a kill-count completion counter. Two default coop starts activate separate
areas. Delayed target deliveries can survive timer shutoff. A ten-minute run is
more informative than stopping at the first timer shutdown. See
[terrain and wave review](terrain-review.md) for the source-derived schedule and
any diagnostic runtime limitations.

## Supplied-source map compilation

The repository now preserves the exact supplied source in
`maps/source/pp_sandbox_coop1.map`. It does not include a verified original
distributed BSP or the author's original compile logs. Install a compatible
q2tool and supply the complete texture/data directory:

```sh
./compile_map.sh --source maps/source/pp_sandbox_coop1.map \
  --tool /path/to/q2tool --basedir /path/to/runtime/baseq2 --threads 2
```

**The compile asset directory must contain a loose `pics/colormap.pcx`**, in
addition to the complete map WAL textures. A normal game installation can load
its palette from `pak0.pak`, but the tested q2tools-220 revision
`07d8d893cb04ba5f39a63d7382e8d9979b3f38da` does not use the `--basedir` PAK as the
expected RAD palette fallback. Merely pointing `--basedir` at an otherwise
working PAK-only game install can therefore fail with
`unable to load pics/colormap.pcx`. Extract that exact PCX entry from the user's
existing game PAK into an isolated compile asset directory at
`<basedir>/pics/colormap.pcx`; keep the original PAK unchanged. Check that the
loose file exists before the long VIS/RAD build. A PNG or a newly generated
palette is not an equivalent input. The wrapper does not extract PAK entries or
patch the external compiler. Its normal stage-failure handling prevents
publication when the palette is unavailable.

Release compilation is the default: BSP, full VIS, then baked lighting. Logs,
commands, tool/source hashes, stage times and the resulting BSP audit are saved
under `build/maps/<map>/`. Leaks, missing textures, failed stages and malformed
or missing visibility/light data prevent publication. A failed build preserves
an existing published BSP.

Preview and missing-texture experiments are explicit:

```sh
./compile_map.sh --source maps/source/pp_sandbox_coop1.map \
  --tool /path/to/q2tool --basedir /path/to/runtime/baseq2 \
  --profile preview --vis --rad --allow-missing-textures
```

`--allow-missing-textures` is diagnostic only and never publishes a release BSP.
Full VIS and source sealing must be verified before attributing sandbox rendering
cost to missing or ineffective visibility. Detail conversion does not remove
rendered polygons. Conservative terrain experiments are kept separate from the
unchanged supplied source.

## Diagnostic pickup and effects scenes

The small reproducible fixture contains two rooms, a doorway, baked lighting and
the same counts of the 16 targeted pickup classes, totaling 92 placements. It is
not the sandbox and contains no wave system. It uses one stock texture from
the user's own data. Generate and compile it with full VIS and lighting:

```sh
python3 tools/performance/make_fixture.py
./compile_map.sh --source maps/fixtures/pp_perf_fixture.map \
  --tool /path/to/q2tool --basedir /path/to/runtime/baseq2 --threads 2

python3 tools/performance/make_fixture.py --effects \
  --output maps/fixtures/pp_perf_effects.map
./compile_map.sh --source maps/fixtures/pp_perf_effects.map \
  --tool /path/to/q2tool --basedir /path/to/runtime/baseq2 --threads 2
```

The effects variant adds native target_blaster projectiles and target_explosion
events driven by normal func_timer entities. It exercises trails, impact effects,
explosion particles, smoke, sprites and dynamic lighting through the real local
server/client path. It is a diagnostic stress scene, not a gameplay difficulty
change or proof of full sandbox performance.

## Bounded capture runner

From the repository root, substitute each isolated runtime in turn:

```sh
python3 tools/performance/run_benchmark.py \
  --binary /path/to/runtime/quake2 --data /path/to/runtime \
  --label gl1-single-run1 --renderer gl1 --map pp_perf_fixture \
  --players 1 --size 640x480 --frames 1920 --warmup 120 --screenshot

python3 tools/performance/run_benchmark.py \
  --binary /path/to/runtime/quake2 --data /path/to/runtime \
  --label gl1-same-run1 --renderer gl1 --map pp_perf_fixture \
  --players 2 --size 640x480 --frames 1920 --warmup 120 --screenshot

python3 tools/performance/run_benchmark.py \
  --binary /path/to/runtime/quake2 --data /path/to/runtime \
  --label gl1-different-run1 --renderer gl1 --map pp_perf_fixture \
  --players 2 --size 640x480 --frames 1920 --warmup 120 \
  --pose 1 560 0 24 0 180 --screenshot

python3 tools/performance/run_benchmark.py \
  --binary /path/to/runtime/quake2 --data /path/to/runtime \
  --label effects-soak-run1 --renderer gl1 --map pp_perf_effects \
  --players 2 --size 240x240 --frames 18120 --warmup 120 --timeout 720 \
  --set vid_maxfps 30 --set r_perf_gpu 0
```

The runner defaults to VSync off, an effectively uncapped display loop, asynchronous
client updates at the engine's configured cadence, no shadows/MSAA/anisotropy,
normal culling, all entities/particles/lights enabled, picmip 0 and dynamic
lighting enabled. Every setting is saved. Sound initialization is disabled for
these controlled renderer measurements. Repeat with sound and the player's real
settings when assessing total playing performance.

For recorded single-player combat, use `--demo demos/<recording>.dm2` instead of
`--map` and omit `--players`/`--pose`. The runner enables timedemo for fixed
snapshot playback. Standard Quake II demos do not encode multiple local camera
streams; do not label one as a two-player split-screen benchmark. Recordings and
save games must come from the user's data and the compatible game module.

`--pose` calls the existing local teleport cheat after the connection is ready.
It supplies player feet coordinates, adds the existing teleport's 10 Z units,
allows physics to settle and can telefrag overlapping placements. Choose separate
safe locations. Compare the actual view origins/angles in the CSV, not just the
requested inputs. It does not freeze simulation, force equivalent snapshot
histories, or bypass networking.

On a headless development host only, append `--xvfb`; a root-managed test container
can append `--unprivileged nobody` to retain the engine's root-execution guard.
For the reported software-host captures the environment was
`LP_NUM_THREADS=2 LIBGL_ALWAYS_SOFTWARE=1`. Never apply `--xvfb` or the software
environment when measuring Pi hardware acceleration.

Use new labels for every run. Existing configuration, CSV, console and metadata
files are protected against reuse. Timeouts terminate and reap the complete
launcher/X server/engine process group. Perform repeated captures in alternating
revision order on real hardware, with stable clocks and no competing compile
jobs. A single host pass is descriptive evidence, not a confidence interval.

## Capturing an existing playing session

The same instrumentation covers the normal split-screen path, which bypasses
`V_RenderView`:

```text
set r_perf 1
set r_perf_gpu 1
set cl_perf_frames 0
set cl_perf_quit 0
cl_perf_start sandbox-wave-run1
// Play the intended session for at least ten minutes.
cl_perf_stop
```

`cl_perf_start` reserves a fresh set of capture files and refuses to overwrite an
existing label. Keep the same map/save, camera route, weapon/loadout and wave
phase between revisions. Moving cameras and combat introduce changing workloads;
describe those changes rather than treating them as exact equivalent-content
comparisons. Diagnostic hidden-entity/effect tests belong in a separate table.

## Output and interpretation

Each capture saves `*-frames.csv`, `*-views.csv`, `*-settings.txt`, `*-console.log`,
`*-run.json` and its command configuration under `baseq2/perf/`. The runner records
binary, renderer, game module, map, stock PAK and project overlay hashes, operating
system, selected environment variables, settings, duration and return code.
Retain GL_VENDOR, GL_RENDERER and GL_VERSION from the startup log.

```sh
python3 tools/performance/summarize.py \
  /path/to/runtime/baseq2/perf/run1-frames.csv \
  --warmup 120 --json /path/to/results/run1-summary.json
```

The summary reports median, P95, P99, maximum, mean, minimum and the fraction of
complete frames exceeding 33.333 ms. The first completion has no preceding
interval and is excluded. Default warmup removes the first 120 display rows.
Resource registration and startup timing are not included in steady-state timing.

Timing columns are CPU-side wall times unless explicitly named `gpu_ms`:

| Column | Meaning and limitation |
| --- | --- |
| `frame_ms` | Complete display completion to completion, including frame limiting and intervening updates |
| `screen_ms` | Screen rendering/presentation interval inside SCR_UpdateScreen |
| `server_ms` | Shared listen-server frame work; contains simulation and snapshot/send |
| `simulation_ms` | SV_RunGameFrame interval |
| `snapshot_send_ms` | Snapshot construction and local/network message send interval; not serialization alone |
| `client_update_ms` | Client input/network/prediction work around screen rendering; post-screen audio work is charged to the next display interval |
| `prepare_ms` | Shared/per-camera client scene preparation hooks, excluding renderer entry |
| `submit_ms` | Sum of actual per-camera renderer calls; includes visibility/model work and any driver blocking |
| `present_ms` | One SDL/renderer EndFrame; may include queued rendering or swap waits |
| Renderer `visibility_ms`, `model_ms` | Nested preparation measurements with the coverage described in renderer.md |

Do not sum nested columns. A CPU submission interval is not GPU execution time.
Supported desktop drivers use asynchronous timer queries with no glFinish added.
Join each `gpu_origin_serial` to its originating `renderer_serial`; the result
can arrive several views later and be repeated. The summarizer deduplicates
origins and filters by the original frame's inclusion after warmup. Results are
sampled views, not guaranteed coverage of every view or a complete-display GPU
interval. GLES reports unsupported rather than inventing a measurement.

GL1 client-array payload counts describe submitted data, not exact driver DMA.
Static registration totals are separate from per-frame upload counters. World
and model triangle counts exclude sky/effect geometry. Draw counts cover the
renderer view, including effects; HUD is outside those per-view counters.

`rss_kib` is Linux resident process memory sampled every 60 frames. It is neither
VRAM nor total system memory. `monsters` and `dead_monsters` derive from server
flags; death animations can temporarily remain in the living-flag category.
Gibs and some projectiles can also carry `SVF_DEADMONSTER`, so that column is a
flag census, not an exact corpse count. `projectiles_by_effect` is an estimate
based on entity effects; it can include fire puddles and omit other projectiles.
Inspect trends
alongside all in-use edicts, particle activity and actual gameplay. Pool bounds
or a flat short-run RSS trace alone do not prove a ten-minute session is safe.

An external Game Bird SPI transfer process may complete after SDL presentation.
Measure that display transport separately and verify real delivered cadence.
The engine CSV cannot establish transfer latency for an unavailable frontend.
